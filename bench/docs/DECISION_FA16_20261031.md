## 1. Contexte

- Cible : prefill du modèle prod (D=256, GQA 6, n_kv≈114 688, KV q8_0, `-b 2048`).
- Diagnostic initial (`pf_ncu_summary.md`) : le kernel FA `flash_attn_ext_f16<256,256,32,2>`
  (32x2, 67.58 KB smem → 1 block/SM, 255 regs) est **latency/occupancy-bound** :
  HMMA 27.4 %, occupancy 6.25 %, DRAM 4.7 %. FA = **49.1 % du prefill prod**.
  NCU OPT : ~93 % de local speedup potentiel si on libère l'occupancy.
- Le build `v100/dual-arch` contenait déjà un **kernel compact**
  (`flash_attn_ext_f16_volta_compact<256,256,32,2>`, 49.15 KB smem → **2 blocks/SM**)
  dont le gate `use_volta_2cta` (T < 1024) ne passait pas au shape prod T=2048.

## 2. Patch (source `v100/dual-arch`, build dual sm_70+sm_61)

Deux env dans `ggml-cuda`, gated à la géométrie prod (cc Volta, DKQ=DV=256, ncols2=2, T≥128) :

| Env | Fichier | Effet |
|---|---|---|
| `GGML_CUDA_VOLTA_FA_NCOLS1=16\|32` | `fattn.cu` (~L200) | force le tile ncols1 du `flash_attn_ext_f16` (16 = 35 KB smem, 2 blocks/SM) |
| `GGML_CUDA_VOLTA_FA_COMPACT_TMAX=N` | `fattn-mma-f16.cuh` (~L2549) | 0=off ; >0 = T max pour router vers le kernel compact 48 KB |

Aucun env → comportement strictement identique à avant le patch.
Artefacts build : `.so` `d4954502` (193 MB, sm_70+sm_61, test_so.sh OK) ;
backups `*.pre-fa16-20261031-151509`.

## 5. Décision

**Adopter C (compact, `GGML_CUDA_VOLTA_FA_COMPACT_TMAX=8192`).**

- B (16x2) est **dominé par C** partout (NCU 183 vs 135 ms ; e2e +7.1 % vs +19.4 %
  @114k). Le garder uniquement en fallback si le kernel compact pose problème à l'usage.
- Gain réel attendus : **prefill +19–21 % sur les charges 98–131k** (règne prod ~115k),
  +5 % sur les courts (16k) ; decode sans impact (prouvé) ; GEMM/FFN intouchés.
- **Risque contenu** : env seul (0 code si on ne change pas le .so servi), rollback
  trivial (unset env, ou restaurer le .so prod `8035caf4` — intact).
- **Rollout, 2 options** (choisir avant tout déploiement) :
  1. Servir le `.so` dual-arch `d4954502` + `GGML_CUDA_VOLTA_FA_COMPACT_TMAX=8192`
     sur le service (zéro rebuild).
  2. Upstream : changer le défaut du gate `use_volta_2cta` (T<1024 → T<8192, ou
     l'aller par défaut quand l'env est vide) + rebuild prod.
- **Decode / MTP : structurellement intouchés (prouvé par le code, pas par la mesure).**
  Le gate compact vit dans `if constexpr (DKQ==256 && DV==256 && ncols1==32 && ncols2==2)`
  (`fattn-mma-f16.cuh`), donc **uniquement dans l'instantiation `<32,2>`**. Le dispatch
  D=256/GQA6/`<ncols2=2>` renvoie à `case<256,256,16,2>` pour **T ≤ 16** (L216) et à
  `case<256,256,32,2>` pour **T > 16**. Decode (T=1) et MTP verify (T ≈ 1+n_max, « 4-6)
  prennent la branche `<16,2>` → le constexpr compact y est `false` (kernel non compilé).
  L'env `TMAX` n'a d'effet que sur `<32,2>`. ⇒ ni le decode ni MTP ne peuvent être affectés.
  (NB : le microbench T=1 « A==C » était une tautologie — 3 legs = même kernel `<16,2>` ;
  le vrai filet decode = le thermal check e2e qui a imputé l'écart à l'ordre du run.)
- **À confirmer au rollout** (un seul point réel, car seul le prefill est modifié) :
  - Le **gain prefill** tient-il dans la stack prod complète MTP-ON + `SPEC_MTP_DEFER_PROMPT=1`
    (le prompt est prefillé en chunks T=2048 → c'est bien la branche `<32,2>` qui gagne) ?
    Mesure de confirmation du win, pas une question de régression MTP/decode.
  - (orthogonal, config future) `Q8_FATTN_TC=1` : si la prod active un jour le Q8 FA, le
    kernel de base change (f16→Q8) → re-mesurer le levier compact f16.
  - Protocole A/B au rollout : alterner l'ordre (A puis C, C puis A) — l'ordre seul vaut
    ~5 t/s de decode apparent à 131k (chauffe GPU).
